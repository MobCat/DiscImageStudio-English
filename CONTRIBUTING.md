# Contributing to Disc Image Studio

Welcome, and thanks for helping with Disc Image Studio. Please read this document first; it covers reporting issues, setting up a development environment, the module-boundary rules, verification requirements and the submission flow.

## Reporting issues

Use GitHub Issues for ordinary problems, and include in the description:

- The app version and how you obtained it (source build / MSIX package), plus your Windows version.
- Steps that reproduce the problem reliably, the expected behaviour and the actual behaviour.
- Any applicable run log or screenshots.

For burning-related issues, also include the recorder model, firmware version and disc brand/model: the visible result and measured calibration depend heavily on that hardware, and issues without it usually cannot be diagnosed.

**Do not** disclose exploitable security problems in a public issue; submit them through GitHub's private reporting as described in the [security policy](SECURITY.md).

Feature suggestions also go through Issues: describe the problem to solve, the behaviour you want, and whether a workable alternative already exists.

## Development environment

- Windows 10 2004+ or Windows 11.
- The .NET 10 SDK; the repository pins `10.0.x` in `global.json`, so `dotnet` matches it automatically once installed.
- The tests depend on no third-party framework; they are all console regression programs that ship with the repository.

```powershell
git clone <your fork URL>
cd DiscImageStudio
dotnet build DiscImageStudio.slnx --configuration Release
dotnet run --project src/DiscImageStudio.App --configuration Release
```

## Module boundaries

Read the [architecture notes](docs/ARCHITECTURE.md) before changing code. The core trade-off: the shell depends on no particular optical encoding, and media-specific logic stays in the matching module. Review focuses on these rules:

1. Do not put CD/DVD/future Blu-ray physical modulation, error correction, sector organisation or file-system details into `DiscImageStudio.Core` or shared layers.
2. Modules must not read state from GUI controls; all input arrives through `DiscJobRequest`. Modules must not show windows directly.
3. When a low-level algorithm cannot be cancelled safely, `SupportsCancellation` must be `false`.
4. Module IDs and command names are globally unique, and the catalog rejects conflicts at start-up.
5. A new command must be registered in `DiscCommandDescriptor`, with catalog routing tests and a minimal-output smoke test added.

## Coding conventions

- Follow the naming, structure and comment density of the surrounding code; keep the build at zero warnings and zero errors.
- Do not remove or downgrade features just to make the build pass, and do not add backwards-compatibility shims or duplicate implementations on your own.
- Before deleting something that looks intentional, explain the purpose in the issue or PR description.
- Do not commit build output, binary assets, or any private key / PFX file.

## Testing and verification

These must all pass before a Pull Request:

```powershell
dotnet build DiscImageStudio.slnx --configuration Release
dotnet run --project src/DvdImageSolver --configuration Release -- selftest
dotnet run --project tests/DiscImageStudio.ArchitectureTests --configuration Release
```

Add verification appropriate to the change and state the result in the description:

- When changing image layout, streaming burn or disc-preset parsing, cross-check your conclusion against the matching regression entry in [VALIDATION.md](docs/VALIDATION.md).
- When changing the GUI, use off-screen rendered screenshots to check the key pages yourself, and update `docs/images/` where necessary. The README screenshots in every language are regenerated by `tools/ReadmeScreenshots/Update-ReadmeScreenshots.ps1`; see its [README](tools/ReadmeScreenshots/README.md).
- After changing an encoding chain such as delayed interleaving, EFMPlus or ECC, explain the change even when the `selftest` coverage items are unchanged.

## Commits and Pull Requests

1. Fork (or branch off `main`) a feature branch; one branch solves one thing, and keep the diff reviewable.
2. Use a short descriptive commit title; the body should explain the behaviour change, how it was verified, and whether large files are produced. Do not overuse emoji!
3. The PR description should state the motivation, the scope of the change and the verification result; when user-visible behaviour changes, update the Unreleased section of `CHANGELOG.md` and the relevant `docs/` documents in the same PR.
4. After pushing, confirm that the GitHub Actions `build` workflow is green.

For large changes (a new module, a new UI page, a change to the burning-layer contract) it is worth opening an issue or draft PR to discuss the approach before writing the implementation.

## Versioning and releases

The project uses `main` plus short-lived feature branches, with semantic versioning that increments for fixes, features and breaking changes. Day-to-day contributions record changes under `Unreleased` in `CHANGELOG.md`; the maintainer updates the version settings in `Directory.Build.props` and the matching version record in the same release-preparation PR, and after it is merged into `main` GitHub Actions generates the version tag and release draft automatically. Ordinary code pushes do not create a release. See the [release guide](docs/RELEASING.md) for the full trigger conditions, pre-release suffixes, draft review and retry rules.
